# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal location-tracking web app ("OwnTracks"-style). Phone GPS loggers (OwnTracks, ulogger, GPS Logger) POST position pings to a Flask server, which stores them in SQLite and renders Google Maps views of tracks, plus choropleth maps (via Plotly) of US counties/states/countries visited. Runs as a single Docker container behind a Cloudflare tunnel + Traefik, with Authelia handling auth on most routes.

## Running it

There is no local dev workflow beyond running the Flask app directly — this project is normally deployed via Docker Compose on the host machine, not run/tested by a coding agent.

- `docker-compose up --build` — builds from `config_files/Dockerfile` and starts the `location_track` service (container command: `sh /project/config_files/startup.sh`).
- `config_files/startup.sh` starts `cron` and launches gunicorn on `serve_flask_interface:app` (port 5000).
- Local/manual run (outside Docker): `python serve_flask_interface.py` runs Flask's dev server on port 8090.
- Requires a `.env` file (see `.env_template`) with `WEBAPP_DOMAIN`, `PASSWORD`, `GMAP_API_KEY`.
- No test suite or linter is configured. `test_flask.py` is a legacy/experimental copy of the Flask app, not a pytest suite.

### Data locations
- SQLite DB path is set in `config.py` (`database_location`, currently `/data/location.sqlite`). In the container, `/data` is bind-mounted from `/mnt/fast_storage/appdata/location_tracks`.
- The whole repo is bind-mounted into the container at `/project` (see `docker-compose.yml`), so code changes take effect without rebuilding the image — only a container restart is needed unless dependencies change.

## Architecture

### Database layer — `location_db.py`
`locationDB` wraps a SQLAlchemy Core (not ORM) SQLite database with four tables: `positions` (raw GPS points), `users` (maps a device/user string to an id), `counties` (all US counties, FIPS-keyed, with `visited`/`year`), `countries` (world countries, with `visited`). It self-migrates on construction (adds missing columns/tables via `ALTER TABLE`/`create_all`, checked on every startup) and seeds `counties`/`countries` from `config_files/state_and_county_fips_master.csv` and `config_files/countries.csv` if empty. Almost all cross-file interaction with data goes through this class — there is no ORM model layer elsewhere.

### Web layer — `serve_flask_interface.py`
The live entrypoint (`serve_flask_interface:app`, per `startup.sh`). Uses `flask_classful`'s `FlaskView` (class `FlaskApp`) to define routes as methods; `FlaskApp._initilization()` is called once at import time (a documented hack, see comment at bottom of file, to work around `flask_classful` re-running `__init__` per request). Key routes:
- `/` — main Google Map view of tracked points/polylines over a date range (`start`/`end` query params); `?points=1` switches from a polyline to individual deletable markers.
- `/log`, `/client/index.php` — ingestion endpoints for OwnTracks (`/log`) and ulogger (`/client/index.php`) apps.
- `/counties`, `/states`, `/countries`, `/state_view` — Plotly choropleth dashboards of visited areas, rendered into `templates/notdash.html`.
- `/log_flight` — scrapes a FlightAware KML URL and inserts it as a track (see also `addpoints_flightaware_kml.py`).
- `/execute_delete` — deletes a point by id (used by the marker delete-button popups on `/?points=1`).
- Most routes are gated by `@authelia_required`, which checks/verifies an `authelia_session` cookie against an external Authelia instance (`AUTHELIA_URL`); ingestion routes (`/log`, `/client/index.php`) are intentionally left open so logger apps can POST without a browser session.
- `plotly_flask.py` is an older/alternate version of this same app — not the one actually served; check `startup.sh`/`docker-compose.yml` before assuming which file is live.

### County/state "visited" computation — `add_county_visits.py`
Run periodically via cron (`config_files/cronjob_daily.sh` → `add_county_visits.py`), not on the request path. `CountyAdder` walks unprocessed `positions` rows in time order and does point-in-polygon lookups against the county GeoJSON (`config_files/gz_counties_*.json`, loaded via geopandas) to mark counties visited. Two optimizations that matter when touching this file:
1. `config.frequent_counties`/`frequent_areas` are bounding boxes for places visited often; points inside them are handled by cheap bbox checks (only the latest point per pass is polygon-tested) instead of a full GeoJSON lookup for every point.
2. `calculate_speeds` estimates speed from neighboring points and filters out points faster than `speed_thresh` (45 m/s) so that airplane flights don't falsely mark every county overflown as "visited."
Points are marked `county_processed` once handled so re-runs are incremental.

### Data ingestion scripts (one-off / cron, not imported by the web app)
Each of these populates `positions` via `location_db.insert_location`, from a different data source: `addpoints_google_takeout.py` (Google Takeout location history), `addpoints_gpx_google.py`/`add_gpx_route_certain_time.py` (GPX files), `addpoints_csv_flightradar.py`/`addpoints_flightaware_kml.py` (flight tracking exports), `add_historical_counties.py` (backfilling county visits for historical/manual data). `cleanup_remove_spurious_areas.py` and `tmp_show_one_state.py` are maintenance/debug utilities. `config_files/cronjob_15_min.sh` runs `addpoints_gpx_google.py` every 15 minutes.

### Travelling salesman experiments
`travelling_salesman.py` and `google_travelling_salesman.py` are standalone route-optimization experiments (using `python_tsp`, `fast_tsp`, `ortools`) against `config_files/usa3100_mixed.tsp` — unrelated to the location-logging/visited-counties functionality and not wired into the Flask app.

### Config — `config.py`
Central place for file paths (all under `config_files/`), the `frequent_counties`/`frequent_areas` bounding boxes used by `add_county_visits.py`, and the US state name ↔ abbreviation maps used throughout the templates and Flask routes. Import `config` rather than hardcoding these paths/maps elsewhere.

## Dev environment (this worktree)

This directory is a `git worktree` of `location_track` (prod), checked out on a separate branch, sharing the same `.git` history — commits made here are immediately visible from the prod checkout via `git log`, no push/pull needed. It runs as its own Docker container (`location_track_dev`, image `location_dev_img`) alongside prod, on its own DB copy (`/mnt/fast_storage/appdata/location_tracks_dev/location.sqlite`, cloned once from prod and now independent) and its own tunnel hostname (`dev_owntracks.exploretheworld.tech`). `config_files/startup.sh` here runs gunicorn with `--reload` and `serve_flask_interface.py` sets `TEMPLATES_AUTO_RELOAD = True` — both dev-only conveniences (not present in prod) so `.py` and template edits show up on refresh without a manual container restart. Prod (`location_track`, `main` branch, container `location_track`) intentionally lacks these.

**`--reload` gotcha: it only recovers from per-request errors, not import-time ones.** If an edit introduces an error that happens at *module import* (e.g. `_initilization()` throwing, or a bad top-level import) rather than inside a request handler, the gunicorn worker fails to boot at all, and after enough failed boot attempts gunicorn's **master** process gives up and exits too — taking `--reload`'s file-watcher down with it. The container itself stays "Up" (`config_files/startup.sh`'s own `while true; do sleep 10; done` is what Docker is actually watching, and `cron` is a separate process), but the site is fully down and no further file save will trigger a reload, since the thing that watches files is gone. Recovery: fix the bug, then manually relaunch gunicorn inside the container (`docker exec -d -w /project location_track_dev /usr/local/bin/python /usr/local/bin/gunicorn --reload -b 0.0.0.0:5000 serve_flask_interface:app`) rather than just waiting for auto-reload. `docker exec -d` output doesn't appear in `docker logs`, so confirm it actually came up with a real request (`docker exec location_track_dev python3 -c "import requests; print(requests.get('http://localhost:5000/<route>', allow_redirects=False).status_code)"`) rather than trusting the log tail, which will otherwise keep showing the stale crash from before the manual restart.

### Counties map (`/counties`)
Rebuilt around three `go.Choroplethmapbox` subplots (continental US, plus small Alaska/Hawaii insets — mapbox has no native inset projection the way the old `scope="usa"` geo trace did) instead of a single static geo/choropleth trace, because the old geo trace was a fixed-aspect SVG projection that always letterboxed inside a mismatched container and couldn't be fixed with CSS alone. Alaska/Hawaii bounds/center/zoom are computed at startup in `FlaskApp._initilization()` via geopandas (see `_mercator_y`/`_mercator_center_lat`/`_fit_zoom`/`_pad_bounds` module-level helpers) and corrected again client-side in `notdash.html`'s JS after the page loads, since the server can't know the visitor's actual screen size. A horizontal/vertical (by orientation) slider replaced the static "Year" colorbar; see the schema-change note above for its current data limitation.

Alaska/Hawaii's counties are colored on the main subplot's trace *in addition to* their dedicated insets, not instead of them -- the insets stay for an always-visible view, but since the main map is a real pannable/zoomable tile map now (not a fixed projection), panning/zooming out far enough to actually reach Alaska or Hawaii's true location should show them colored rather than a blank basemap. Same treatment on `/states`' main trace.

A 4th trace overlays state boundaries on the main subplot (`/counties` only -- on `/states` the choropleth polygons already *are* state boundaries, so it'd be redundant there): `self.states_geojson` again, transparent fill (`colorscale=[[0,'rgba(0,0,0,0)'],[1,'rgba(0,0,0,0)']]`, its own standalone colorscale rather than the shared `coloraxis`, so it can't ever pick up a real fill color) and a thicker/darker line (`1.5`/`#333`) than the county borders beneath it (`0.4`/`#888`), so state lines stay readable at a glance even zoomed into county-level detail. `hoverinfo='skip'` keeps it from swallowing hover tooltips meant for the county layer. It does still carry a (constant, all-zero) `z` array, so the year-slider JS includes it in every `Plotly.restyle` call along with the real traces -- harmless (0 never exceeds any realistic cutoff, confirmed against the actual rendered data), just a few unnecessary bytes per slider move, not worth the complexity of excluding it.

### Countries map (`/countries`)
Same `go.Choroplethmapbox` approach as counties, but one full-domain subplot (a world view has no AK/HI-style inset problem). Country boundaries come from `config_files/world-countries.geojson` (238 features, `id`'d by ISO alpha-3 to match `location_db`'s `countries.code_3`/`countries.csv`'s `alpha-3`), generated once from https://github.com/datasets/geo-countries (itself Natural Earth-derived) with two fixups applied before vendoring it in: large countries' coastlines simplified (`shapely.simplify`, ~2km tolerance, only for countries whose bbox exceeds 3°) to cut the file from 14.6MB to 2.9MB, and France/Norway's ISO codes — which that source leaves as the placeholder `"-99"`, a known issue in Natural Earth-derived country datasets — corrected by name lookup against `countries.csv`. 20 non-ISO/disputed territories (Kosovo, sovereign base areas, uninhabited islands, etc.) were dropped entirely since nothing in this app can ever mark them "visited" anyway; 11 more (French/Dutch overseas departments, a few uninhabited islands) aren't broken out as separate shapes in the source data and so can't be shown individually if ever marked visited — both are cosmetic edge cases, not routes to a broken page.

Each visited country gets its own color (`_country_color`) rather than one shared "visited" color, so adjacent visited countries don't blend into a single blob -- explicitly *not* real four-color-theorem map coloring (no adjacency data, no constraint solving), just a hash-seeded HSL hue per ISO code with fixed saturation/lightness (so every color comes out equally vivid regardless of hue) -- two neighboring countries can in principle still land on similar colors, an accepted tradeoff for staying simple. Hashed rather than using `random` so a given country's color is stable across reloads instead of reshuffling every page load. Technique: since a single `z`/`colorscale` normally produces one continuous gradient, each country is given its own "category" (0 = unvisited, sharing a single neutral color; 1..N = one per visited country) and the colorscale is built with two stops at the start/end of each category's slice (same color at both), which makes plotly render a hard-edged flat block per category instead of interpolating between them.

The page also carries the same card-grid list styling `_compute_table` uses for `/states` (via a new `_compute_country_cards` — cards have no href, since there's no per-country drill-down page the way `state_view` drills down from a state). This is the first page to combine a full-bleed map with a table: those were previously mutually exclusive, selected implicitly by whether `more_html` was passed (table ⇒ contained 55vh map, no table ⇒ full-bleed). Now there's an explicit `full_bleed_map` flag passed to `render_template` (`/counties`, `/countries`, and now `/states` set it; `state_view` alone doesn't), and `notdash.html`'s CSS lets a `.table-container` coexist with the fixed-position full-bleed `#chart`.

The first version pushed the table down with `margin-top: 100svh` so the map was fully visible on load, with the card list meant to scroll up over it like a bottom sheet -- but on mobile this trapped scrolling entirely. `#chart` is `position: fixed`, so at 100svh tall it covers the *whole* viewport at *every* scroll position, not just at the top; combined with `touch-action: none` (needed so a drag pans the map instead of the page), that left no spot on screen a touch could land on to start a native scroll once the header bars scrolled out of view -- stuck with neither the buttons nor the table reachable, un-recoverable short of reloading. Fixed by adding a `with-table` body class (set when a page is both `full_bleed_map` and has `more_html`) that caps `#chart` to 90vh/90svh instead of 100 on those pages only -- `/counties` alone is untouched and stays full 100svh, since it has nothing to scroll to in the first place. The remaining 10% is never covered by the fixed map regardless of scroll position, so there's always a strip native touch-scroll can grab. This fix has not yet been re-confirmed on a real device.

Also found (fixed in the same pass): the autocomplete dropdown from `.country-bar` (below) was rendering *behind* `.title-bar`'s text. Not a plain z-index magnitude problem -- `.country-bar` had `position: relative` promoting it to its own stacking context (needed for the "paint above the fixed map" treatment all the header bars get), so the dropdown's z-index only ranked it against siblings *inside* `.country-bar`; the bar itself was tied at z-index:1 with `.title-bar` and lost that tie by coming first in the DOM. Fixed by giving `.country-bar` its own higher z-index (3) rather than sharing the combined `.top-bar, .country-bar, .title-bar` rule.

### States map (`/states`)
Same rebuild as counties/countries: `go.Choroplethmapbox` (continental + AK/HI insets, states has the same "Alaska is far away" problem) replacing the old `px.choropleth(scope='usa')`, full-bleed layout (`full_bleed_map=True`) with the existing `_compute_table` card grid below it (unchanged -- same cards `/states` always had, just now sitting under a real map instead of a letterboxed one). Colored by visit year, like counties -- unlike `/countries`, states does track a year (`location_db.get_state_visits_dataframe`), so this got the year gradient + slider instead of countries' binary visited/unvisited color; `get_state_visits_dataframe` now applies the same -2000 offset `get_county_visits_dataframe` does, since both feed the same slider JS (which hardcodes `YEAR_BASE = 2000`) -- it didn't before, since nothing consumed it that way yet.

State outlines needed a states-level GeoJSON, which didn't exist -- rather than sourcing another external file (as `/countries` needed to), `_initilization()` now dissolves the county polygons already loaded for `/counties` up to state boundaries via `geopandas.dissolve()`, keyed by the FIPS→state mapping `get_county_visits_dataframe()` already provides. Adds a few seconds to every startup (dissolving ~3200 county polygons into 51 states); state outlines aren't simplified the way `world-countries.geojson`'s large countries are, so the resulting file is comparably sized to the county one despite having far fewer features -- untouched so far since nothing's indicated it needs to be, not because it was checked and found fine.

The Alaska/Hawaii inset math (domain/zoom/center/pan-bounds) was previously computed inline inside the counties precompute method; pulled out into a shared `__mapbox_layout_base()` helper so `/states` doesn't duplicate it -- purely geometric, independent of whether counties' or states' data ends up colored on top. Confirmed byte-identical inset output for both pages post-extraction.

**Building this took the dev site down** -- a `NameError` (`mapping` used before its import was added) crashed `_initilization()` at *import* time, which gunicorn's `--reload` can't recover from the way it recovers from a per-request error: the worker failed to boot, and after enough failed attempts gunicorn's master process exited entirely, taking the `--reload` file-watcher down with it. Fixed the bug, then had to manually relaunch gunicorn (`docker exec -d`) rather than just waiting for auto-reload, since the watcher was gone -- see the callout in "Dev environment" above. Confirmed back up via a direct HTTP request afterward, not just by process-list/log inspection.

### Add Country autocomplete
The `.country-bar` form (shared top nav, present on every page) filters the full country list client-side as you type, matching name or either ISO code, ranked so "starts with" matches (including exact code matches) come before "contains" matches, capped to 8 shown. Picking a suggestion just fills the input -- submission is still the existing explicit Submit button/Enter, no auto-submit-on-pick. The full name/code list is precomputed once as `FlaskApp.country_list_json` in `_initilization()` (static once seeded, no need to requery per request) and injected into every template via `@app.context_processor` (`inject_country_list`), since the form isn't tied to any one route.

Building this surfaced a real pre-existing data bug: pandas' default NA-sentinel list includes the literal string `"NA"`, which is Namibia's actual ISO alpha-2 code, so it silently read as a missing value while seeding the DB from `countries.csv` -- Namibia's `code_2` was `NULL` in the database (confirmed to be the only country affected; checked the whole CSV against pandas' full sentinel list). Fixed both ends: `keep_default_na=False` on the CSV read prevents it on any future fresh seed, and `locationDB.__init__` now self-heals any existing NULL `code_2`/`code_3` row by looking it up from the CSV by name on every startup (a no-op once fixed, same "repair on startup if needed" pattern the schema-migration checks above it already use).
