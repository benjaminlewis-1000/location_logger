# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal location-tracking web app ("OwnTracks"-style). Phone GPS loggers (OwnTracks, ulogger, GPS Logger) POST position pings to a Flask server, which stores them in SQLite and renders Google Maps views of tracks, plus choropleth maps (via Plotly) of US counties/states/countries visited. Runs as a single Docker container behind a Cloudflare tunnel + Traefik, with Authelia handling auth on most routes.

## Running it

There is no local dev workflow beyond running the Flask app directly — this project is normally deployed via Docker Compose on the host machine, not run/tested by a coding agent.

- `docker-compose up --build` — builds from `config_files/Dockerfile` and starts the `location_track` service (container command: `sh /project/config_files/startup.sh`).
- `config_files/startup.sh` launches gunicorn on `serve_flask_interface:app` (port 5000) and starts `cron` — except in dev, where cron is skipped (see "Dev environment" below).
- Local/manual run (outside Docker): `python serve_flask_interface.py` runs Flask's dev server on port 8090.
- Requires a `.env` file (see `.env_template`) with `WEBAPP_DOMAIN`, `PASSWORD`, `GMAP_API_KEY`.
- No test suite or linter is configured.

### Data locations
- SQLite DB path is set in `config.py` (`database_location`, currently `/data/location.sqlite`). In the container, `/data` is bind-mounted from `/mnt/fast_storage/appdata/location_tracks`.
- The whole repo is bind-mounted into the container at `/project` (see `docker-compose.yml`), so code changes take effect without rebuilding the image — only a container restart is needed unless dependencies change.

## Architecture

### Database layer — `location_db.py`
`locationDB` wraps a SQLAlchemy Core (not ORM) SQLite database with six tables: `positions` (raw GPS points), `users` (maps a device/user string to an id), `counties` (all US counties, FIPS-keyed, with `visited`/`year` — `year` is the *most recent* visit year, a cache, see "County visit-years" below), `countries` (world countries, with `visited`), `county_visits` (`fips`, `year`, composite PK — one row per distinct visit-year, the full history `counties.year` alone can't represent), `historical_points` (raw historical-GPX-trip points, deliberately kept separate from `positions` — see "County visit-years" below). It self-migrates on construction (adds missing columns/tables via `ALTER TABLE`/`create_all`, checked on every startup) and seeds `counties`/`countries` from `config_files/state_and_county_fips_master.csv` and `config_files/countries.csv` if empty. Almost all cross-file interaction with data goes through this class — there is no ORM model layer elsewhere.

**Rule (not a todo, a standing constraint): every schema change must self-migrate on startup, unconditionally.** Dev's database was cloned from prod once (see "Dev environment" below) and has been fully independent ever since — nothing done to it here ever reaches prod's database, including by merging code. So when this branch eventually merges and prod runs the new code, prod's database will still be on the *old* schema at that moment; there is no shared migration step that runs once at deploy time. A new column/table can never be assumed to exist just because it does in dev, or because a fresh DB would have it — the code itself has to detect the absence and add/backfill it, every time, the same way `__init__` already does for the `year`/`county_processed` columns, `populate_countries`/`populate_county_table` seeding empty tables, and the Namibia `code_2`/`code_3` NULL repair. Any future schema addition (e.g. a "flown through" country/table) needs the same treatment, not a one-off migration script.

### Web layer — `serve_flask_interface.py`
The live entrypoint (`serve_flask_interface:app`, per `startup.sh`). Uses `flask_classful`'s `FlaskView` (class `FlaskApp`) to define routes as methods; `FlaskApp._initilization()` is called once at import time (a documented hack, see comment at bottom of file, to work around `flask_classful` re-running `__init__` per request). Key routes:
- `/` — main Google Map view of tracked points/polylines over a date range (`start`/`end` query params); `?points=1` switches from a polyline to individual deletable markers.
- `/log`, `/client/index.php` — ingestion endpoints for OwnTracks (`/log`) and ulogger (`/client/index.php`) apps.
- `/counties`, `/states`, `/countries`, `/state_view` — Plotly choropleth dashboards of visited areas, rendered into `templates/notdash.html`.
- `/log_flight` — scrapes a FlightAware KML URL and inserts it as a track.
- `/execute_delete` — deletes a point by id (used by the marker delete-button popups on `/?points=1`).
- Most routes are gated by `@authelia_required`, which checks/verifies an `authelia_session` cookie against an external Authelia instance (`AUTHELIA_URL`); ingestion routes (`/log`, `/client/index.php`) are intentionally left open so logger apps can POST without a browser session.
- This is now the only Flask app file in the repo. Two earlier superseded versions have both been deleted: `plotly_flask.py` (before this session) and `test_flask.py` (this session — confirmed dead first: `startup.sh` only ever launched `serve_flask_interface:app`, and `serve_flask_interface.py` already had its own equivalent `/log`/`/client/index.php` routes, so nothing was actually relying on it. Its one remaining referrer, `cleanup_remove_spurious_areas.py`, was switched to get its DB connection via `location_db`/`config` like every other script before the file was removed).

### County/state "visited" computation — `add_county_visits.py`
Run periodically via cron (`config_files/cronjob_daily.sh` → `add_county_visits.py`, wrapped in `flock` — see "County visit-years" below), not on the request path. `CountyAdder` walks unprocessed `positions` rows in time order and does point-in-polygon lookups against the county GeoJSON (`config_files/gz_counties_*.json`, loaded via geopandas) to mark counties visited. `CountyAdder(mode='ongoing'|'backfill')` selects which `positions` tracking column drives that walk and where visits get recorded — see "County visit-years" below for the full split. Two optimizations that matter when touching this file:
1. `config.frequent_counties`/`frequent_areas` are bounding boxes for places visited often; points inside them are handled by cheap bbox checks instead of a full GeoJSON lookup for every point — one polygon lookup per (frequent county × distinct calendar year present in that batch), not per point.
2. `calculate_speeds` estimates speed from neighboring points and filters out points faster than `speed_thresh` (45 m/s) so that airplane flights don't falsely mark every county overflown as "visited."
Points are marked processed (on whichever tracking column the current mode uses) once handled so re-runs are incremental.

### Data ingestion scripts (one-off / cron, not imported by the web app)
Each of these populates `positions` via `location_db.insert_location`, from a different data source: `addpoints_google_takeout.py` (Google Takeout location history), `addpoints_gpx_google.py` (GPX files, cron'd every 15 min). `add_gpx_route_certain_time.py` and `addpoints_csv_flightradar.py` (flight tracking exports) are both currently broken — see "Known issues" below, left in place for now rather than deleted. Historical/pre-GPS-era GPX trips are a separate case, deliberately *not* funneled into `positions` — see "County visit-years" below for the current `historical_points`/`load_historical_points.py`/`process_historical_points.py` design, which supersedes `add_historical_gpx_points.py` and `add_historical_counties.py` (both deleted). `cleanup_remove_spurious_areas.py` is a maintenance utility. `config_files/cronjob_15_min.sh` runs `addpoints_gpx_google.py` every 15 minutes; `cronjob_daily.sh` runs `add_county_visits.py` hourly (despite the filename — was every 6h, changed to hourly).

### Travelling salesman experiments
`travelling_salesman.py` and `google_travelling_salesman.py` are standalone route-optimization experiments (using `python_tsp`, `fast_tsp`, `ortools`) against `config_files/usa3100_mixed.tsp` — unrelated to the location-logging/visited-counties functionality and not wired into the Flask app.

**Future idea, not yet investigated or designed**: extend these experiments into a real feature on `/counties`/`/state_view` — given the current set of *unvisited* counties (either within one state, or across the whole continental US), compute an approximate shortest route connecting all of them, as a suggested trip for closing out the map. `usa3100_mixed.tsp` is a static, pre-built full-USA problem instance; a real feature would need to build a fresh instance on the fly from the actual unvisited-county centroids for whatever scope was requested, not reuse that file directly. Nothing about UI placement, how a county reduces to a single routable point (centroid? most-central town?), or which of the three already-experimented-with solvers fits an interactive request/response time budget (a nationwide unvisited-county set could be large) has been looked at yet.

### Config — `config.py`
Central place for file paths (all under `config_files/`), the `frequent_counties`/`frequent_areas` bounding boxes used by `add_county_visits.py`, and the US state name ↔ abbreviation maps used throughout the templates and Flask routes. Import `config` rather than hardcoding these paths/maps elsewhere.

## Dev environment (this worktree)

This directory is a `git worktree` of `location_track` (prod), checked out on a separate branch, sharing the same `.git` history — commits made here are immediately visible from the prod checkout via `git log`, no push/pull needed. It runs as its own Docker container (`location_track_dev`, image `location_dev_img`) alongside prod, on its own DB copy (`/mnt/fast_storage/appdata/location_tracks_dev/location.sqlite`, cloned once from prod and now independent) and its own tunnel hostname (`dev_owntracks.exploretheworld.tech`). `config_files/startup.sh` here runs gunicorn with `--reload` and `serve_flask_interface.py` sets `TEMPLATES_AUTO_RELOAD = True` — both dev-only conveniences (not present in prod) so `.py` and template edits show up on refresh without a manual container restart. Prod (`location_track`, `main` branch, container `location_track`) intentionally lacks these.

**Cron is intentionally disabled in dev.** Both containers bake in the identical `cron-config` (`*/15` GPX ingest via `addpoints_gpx_google.py`, hourly `add_county_visits.py`), and `startup.sh` used to start it unconditionally — confirmed via `docker exec ... crontab -l` that dev and prod really were running the exact same schedule. There's no live data-collision today (the two DBs are fully separate, and dev's `/data` mount has no `gdrive_data` folder at all, so the GPX job was a no-op there) but it was an unguarded liability with no reason to run in dev. Fixed by adding `APP_ENV=dev` to dev's `docker-compose.yml` only, and gating `cron &` in `startup.sh` on it (`if [ "$APP_ENV" != "dev" ]; then cron & fi`). Prod never sets `APP_ENV`, so it keeps running cron with **no change needed on that side**, now or after this branch eventually merges into `main` — matches the standing rule of never requiring a prod-side edit for dev-side work. The crontab itself is still installed in the dev image either way (`crontab -l` still lists both jobs); it's just never started by `startup.sh` there. `cronjob_daily.sh` itself now wraps `add_county_visits.py` in `flock -n` — see "County visit-years" below.

**`--reload` gotcha: it only recovers from per-request errors, not import-time ones.** If an edit introduces an error that happens at *module import* (e.g. `_initilization()` throwing, or a bad top-level import) rather than inside a request handler, the gunicorn worker fails to boot at all, and after enough failed boot attempts gunicorn's **master** process gives up and exits too — taking `--reload`'s file-watcher down with it. The container itself stays "Up" (`config_files/startup.sh`'s own `while true; do sleep 10; done` is what Docker is actually watching, and `cron` is a separate process), but the site is fully down and no further file save will trigger a reload, since the thing that watches files is gone. Recovery: fix the bug, then manually relaunch gunicorn inside the container rather than just waiting for auto-reload:

```
docker exec -d -w /project location_track_dev sh -c "/usr/local/bin/python /usr/local/bin/gunicorn --reload -b 0.0.0.0:5000 serve_flask_interface:app > /tmp/manual_gunicorn.log 2>&1"
```

Redirect to a file (as above) rather than a bare `docker exec -d ... gunicorn ...` -- `docker exec -d` output doesn't appear in `docker logs` at all, so an unredirected manual launch that crashes again later leaves *nothing* to diagnose it from (this bit once already: a second, still-unexplained crash left only the first crash's now-stale trace visible in `docker logs`). Confirm the relaunch actually came up with a real request (`docker exec location_track_dev python3 -c "import requests; print(requests.get('http://localhost:5000/<route>', allow_redirects=False).status_code)"`) rather than trusting the log tail either way.

## Working conventions

**Explain the plan before implementing it, for anything with real design surface.** New features, schema/DB changes, anything touching multiple files or with more than one reasonable way to build it — say what's about to be built and how (the approach, the pieces/files involved, any real tradeoffs) *before* writing the code, not only after in a summary. Small, obvious, single-file tweaks (a color, a size, a threshold number, a one-line fix) don't need this ceremony — use judgment on which category a change falls into.

**Verify Plotly/mapbox-gl trace capabilities empirically before building on them — don't assume by analogy.** This app leans on several non-obvious trace tricks that do work (a stepped colorscale for discrete per-location colors, a transparent-fill overlay trace for a borders-only layer, per-location `marker.opacity` arrays) but aren't obviously documented as supported. Two things were assumed available and weren't, both on `/countries`' micro-country markers: `marker(symbol='star')` (needs a Mapbox access token this app deliberately doesn't have) and `mode='text'` markers reliably rendering (a mapbox-gl *symbol* layer has collision detection on by default, which can silently drop the marker, and Plotly's declarative API doesn't expose the style-spec property to turn that off — see "Countries map" below for the full story). When a trace attribute's behavior matters, check it directly (e.g. `dir(go.Choroplethmapbox().marker)`, or plotly's own schema/docs) rather than assuming it exists because a similar-looking trace type has it.

**No real browser is available for verifying JS changes here — this environment has neither one nor `jsdom`.** The pattern used throughout this branch: render the real template server-side (Flask's `render_template`/test client) to get genuine output, extract the relevant `<script>` block, `node --check` it for syntax, and for anything with real control flow (the Add Country form, undo stack, zoom-scaling), copy the function bodies verbatim into a small Node script that mocks just enough of `document`/`fetch`/`localStorage`/`Plotly` to exercise the actual logic and assert on outcomes. This has repeatedly caught real bugs (a stray `#`-vs-`//` comment typo, twice; wrong assumptions in a hand-written test's own expected values) before they reached the user, but it's still not a substitute for the genuinely-only-real-browser-catches-it class of bug (the two mapbox-gl rendering misses above were both invisible to this whole toolchain and only found by the user on an actual device) — UI changes should still be reported as unconfirmed until the user actually looks at them.

### Counties map (`/counties`)
Rebuilt around three `go.Choroplethmapbox` subplots (continental US, plus small Alaska/Hawaii insets — mapbox has no native inset projection the way the old `scope="usa"` geo trace did) instead of a single static geo/choropleth trace, because the old geo trace was a fixed-aspect SVG projection that always letterboxed inside a mismatched container and couldn't be fixed with CSS alone. Alaska/Hawaii bounds/center/zoom are computed at startup in `FlaskApp._initilization()` via geopandas (see `_mercator_y`/`_mercator_center_lat`/`_fit_zoom`/`_pad_bounds` module-level helpers) and corrected again client-side in `notdash.html`'s JS after the page loads, since the server can't know the visitor's actual screen size. A horizontal/vertical (by orientation) slider replaced the static "Year" colorbar; see "County visit-years" below for how it works and its data source.

Alaska/Hawaii's counties are colored on the main subplot's trace *in addition to* their dedicated insets, not instead of them -- the insets stay for an always-visible view, but since the main map is a real pannable/zoomable tile map now (not a fixed projection), panning/zooming out far enough to actually reach Alaska or Hawaii's true location should show them colored rather than a blank basemap. Same treatment on `/states`' main trace.

A 4th trace overlays state boundaries on the main subplot (`/counties` only -- on `/states` the choropleth polygons already *are* state boundaries, so it'd be redundant there): `self.states_geojson` again, transparent fill (`colorscale=[[0,'rgba(0,0,0,0)'],[1,'rgba(0,0,0,0)']]`, its own standalone colorscale rather than the shared `coloraxis`, so it can't ever pick up a real fill color) and a thicker/darker line (`1.5`/`#333`) than the county borders beneath it (`0.4`/`#888`), so state lines stay readable at a glance even zoomed into county-level detail. `hoverinfo='skip'` keeps it from swallowing hover tooltips meant for the county layer. It does still carry a (constant, all-zero) `z` array, so the year-slider JS includes it in every `Plotly.update` call along with the real traces (`Plotly.update`, not `Plotly.restyle`, as of the color-scale rescale below -- layout-level `coloraxis` changes need `relayout`-style updates) -- harmless either way: this trace has its own standalone colorscale, not the shared `coloraxis`, so it's structurally unaffected by any `coloraxis.cmin`/`cmax` changes, just a few unnecessary bytes per slider move, not worth the complexity of excluding it.

### Countries map (`/countries`)
Same `go.Choroplethmapbox` approach as counties, but one full-domain subplot (a world view has no AK/HI-style inset problem). Fill opacity is per-country (`marker.opacity` takes an array, same as `z`): 0 for unvisited so the basemap shows through untinted, 0.5 for visited so it's still partly visible under the color. Borders stay fully opaque regardless -- `marker.line` (the border) is a separate style layer from the fill in mapbox-gl, with its own independent opacity, so country outlines remain visible everywhere. Country boundaries come from `config_files/world-countries.geojson` (238 features, `id`'d by ISO alpha-3 to match `location_db`'s `countries.code_3`/`countries.csv`'s `alpha-3`), generated once from https://github.com/datasets/geo-countries (itself Natural Earth-derived) with two fixups applied before vendoring it in: large countries' coastlines simplified (`shapely.simplify`, ~2km tolerance, only for countries whose bbox exceeds 3°) to cut the file from 14.6MB to 2.9MB, and France/Norway's ISO codes — which that source leaves as the placeholder `"-99"`, a known issue in Natural Earth-derived country datasets — corrected by name lookup against `countries.csv`. 20 non-ISO/disputed territories (Kosovo, sovereign base areas, uninhabited islands, etc.) were dropped entirely since nothing in this app can ever mark them "visited" anyway; 11 more (French/Dutch overseas departments, a few uninhabited islands) aren't broken out as separate shapes in the source data and so can't be shown individually if ever marked visited — both are cosmetic edge cases, not routes to a broken page.

Each visited country gets its own color (`_country_color`) rather than one shared "visited" color, so adjacent visited countries don't blend into a single blob -- explicitly *not* real four-color-theorem map coloring (no adjacency data, no constraint solving), just a hash-seeded HSL hue per ISO code with fixed saturation/lightness (so every color comes out equally vivid regardless of hue) -- two neighboring countries can in principle still land on similar colors, an accepted tradeoff for staying simple. Hashed rather than using `random` so a given country's color is stable across reloads instead of reshuffling every page load. Technique: since a single `z`/`colorscale` normally produces one continuous gradient, each country is given its own "category" (0 = unvisited, sharing a single neutral color; 1..N = one per visited country) and the colorscale is built with two stops at the start/end of each category's slice (same color at both), which makes plotly render a hard-edged flat block per category instead of interpolating between them. Hover is overridden (`hovertemplate` + `customdata`) to show just the country name -- by default it'd show the `locations` value (the iso_3 code) and this internal category `z`, neither meaningful to a viewer.

Visited micro-countries (Vatican, and any similarly tiny country visited in the future -- Monaco, San Marino, etc.) are a sub-pixel dot on a world map even though they're technically colored; flagged by bounding-box diagonal (<0.5°, picked from eyeballing the real size distribution -- catches true microstates without also flagging small-but-still-visible countries like Luxembourg or Qatar) and given a marker at their centroid instead, on a second `go.Scattermapbox` trace. Two approaches were tried and discarded before landing on a plain circle (`mode='markers'`):
- `marker(symbol='star')` -- Scattermapbox's icon-based marker symbols come from Mapbox's own hosted sprite set, which needs a Mapbox access token this app deliberately doesn't have (it uses the free, tokenless `carto-positron` style specifically to avoid that).
- `mode='text'` with a unicode star glyph -- avoids the token problem, but confirmed invisible on a real device (Vatican, zoomed into Rome). Best explanation: this compiles to a mapbox-gl *symbol* layer, and symbol layers have collision detection on by default -- if mapbox-gl decides the glyph would overlap a basemap label (a city/sea name, etc.) at that zoom, it silently drops it, and Plotly's declarative Scattermapbox API doesn't expose the underlying style-spec property (`text-allow-overlap`) to disable that.

`mode='markers'` (a plain circle) compiles to a mapbox-gl *circle* layer instead, which isn't part of that collision system -- it always draws regardless of nearby labels. This is a reasoned fix for a bug that could only be confirmed on a real device, not reproduced locally -- worth re-checking if micro-country markers ever go invisible again.

The page also carries the same card-grid list styling `_compute_table` uses for `/states` (via a new `_compute_country_cards` — cards have no href, since there's no per-country drill-down page the way `state_view` drills down from a state). This is the first page to combine a full-bleed map with a table: those were previously mutually exclusive, selected implicitly by whether `more_html` was passed (table ⇒ contained 55vh map, no table ⇒ full-bleed). Now there's an explicit `full_bleed_map` flag passed to `render_template` (`/counties`, `/countries`, and now `/states` set it; `state_view` alone doesn't), and `notdash.html`'s CSS lets a `.table-container` coexist with the fixed-position full-bleed `#chart`.

The first version pushed the table down with `margin-top: 100svh` so the map was fully visible on load, with the card list meant to scroll up over it like a bottom sheet -- but on mobile this trapped scrolling entirely. `#chart` is `position: fixed`, so at 100svh tall it covers the *whole* viewport at *every* scroll position, not just at the top; combined with `touch-action: none` (needed so a drag pans the map instead of the page), that left no spot on screen a touch could land on to start a native scroll once the header bars scrolled out of view -- stuck with neither the buttons nor the table reachable, un-recoverable short of reloading. Fixed by adding a `with-table` body class (set when a page is both `full_bleed_map` and has `more_html`) that caps `#chart` to 90vh/90svh instead of 100 on those pages only -- `/counties` alone is untouched and stays full 100svh, since it has nothing to scroll to in the first place. The remaining 10% is never covered by the fixed map regardless of scroll position, so there's always a strip native touch-scroll can grab. Confirmed working on a real mobile device.

Also found (fixed in the same pass): the autocomplete dropdown from `.country-bar` (below) was rendering *behind* `.title-bar`'s text. Not a plain z-index magnitude problem -- `.country-bar` had `position: relative` promoting it to its own stacking context (needed for the "paint above the fixed map" treatment all the header bars get), so the dropdown's z-index only ranked it against siblings *inside* `.country-bar`; the bar itself was tied at z-index:1 with `.title-bar` and lost that tie by coming first in the DOM. Fixed by giving `.country-bar` its own higher z-index (3) rather than sharing the combined `.top-bar, .country-bar, .title-bar` rule.

### Add Country form
The `.country-bar` form (shared top nav, present on every page) filters the full country list client-side as you type, matching name or either ISO code, ranked so "starts with" matches (including exact code matches) come before "contains" matches, capped to 8 shown. Picking a suggestion just fills the input -- submission is still the existing explicit Submit button/Enter, no auto-submit-on-pick. The full name/code list is precomputed once as `FlaskApp.country_list_json` in `_initilization()` (static once seeded, no need to requery per request) and injected into every template via `@app.context_processor` (`inject_country_list`), since the form isn't tied to any one route.

Building this surfaced a real pre-existing data bug: pandas' default NA-sentinel list includes the literal string `"NA"`, which is Namibia's actual ISO alpha-2 code, so it silently read as a missing value while seeding the DB from `countries.csv` -- Namibia's `code_2` was `NULL` in the database (confirmed to be the only country affected; checked the whole CSV against pandas' full sentinel list). Fixed both ends: `keep_default_na=False` on the CSV read prevents it on any future fresh seed, and `locationDB.__init__` now self-heals any existing NULL `code_2`/`code_3` row by looking it up from the CSV by name on every startup (a no-op once fixed, same "repair on startup if needed" pattern the schema-migration checks above it already use).

**Submission** is a `fetch()` POST (`event.preventDefault()` on the form's `submit`), not a normal browser navigation -- it used to land on `/log_country`'s raw JSON response as its own page. Success/failure now shows as a small inline message next to the form instead (`#country-form-message`); `/log_country`'s "identifier not found" path was changed from rendering `404.html` to returning JSON with the rest, since the client needs one consistent response shape to parse regardless of outcome. On success, only on `/countries` (the only page an added country could visibly affect), the map and card list refresh in place: rather than reimplementing the color/opacity/category logic in JS (which would need to exactly match `_country_color`'s Python-side hashing to avoid a country's color drifting between this live update and the next real reload), it re-fetches the current page's own HTML in the background, pulls the freshly-rendered `graphJSON` and `.table-container` back out of it, and applies them via `Plotly.react()` -- reusing the real server-side rendering rather than duplicating it. Known small gap: if this live refresh causes a micro-country star marker to appear for the first time (e.g. just marked Vatican visited while already on the page), it won't have the zoom-scaling behavior (see "Countries map" above) until an actual reload, since that listener is only ever attached once at initial page load.

**Undo** is a single button (`#undo-country-btn`, hidden when there's nothing to undo) backed by a LIFO stack in `localStorage` (`countryUndoStack` -- `localStorage`, not `sessionStorage`, specifically so it's shared across tabs of the same browser, not just page reloads within one). Each click pops the most recent `{iso_3, name, field}` entry and POSTs it to a new `/undo_country` route, which just forces that one column back to `False` via new `unset_visited_country`/`unset_flown_through_country` methods (mirrors of the existing setters). Clicking repeatedly walks back through the whole session's history, most-recent-first -- there's no separate "undo everything" action, since that's the same thing as clicking this one enough times.

Two real bugs found here by the user in a real browser, both fixed and confirmed working. (1) The button was rendering on `/counties`/`/states`/`/state_view` too, not just `/countries` -- `notdash.html`'s Add Country bar had no page guard, and since the undo stack lives in `localStorage` (shared site-wide), adding a country once made the button linger on unrelated pages. Fixed by gating it behind a `show_country_bar` flag that only `/countries` passes. (2) It also had a hard `max-width:55%` sized for its old spot in the message-row footer, truncating a longer country name down to "Un...". Fixed by moving it into the input row (per the user's ask), with the input itself, not the button, now the primary flex-shrink target; the button also grew a `title` tooltip with the full text as a backstop.

The one real subtlety: not every successful submission is safe to undo. `/log_country` now looks up a country's status *before* mutating it (`get_country_status`, using a `_find_country_row` helper factored out of the three now-similar lookups in `location_db.py`) and includes `was_already_set` in its response; the client only pushes an undo entry when that's `False`. Otherwise, resubmitting a country that's already set (an accidental double-click, or just forgetting it was already added) would push an entry whose "undo" -- forcing the field back to `False` -- could silently erase a fact that's actually true from a completely different, untracked action. A failed undo request puts the popped entry back on the stack rather than losing it, and the button disables itself for the duration of a request to avoid a double-click racing two pops of the same top-of-stack entry -- but only for the actual `/undo_country` round-trip, not the map redraw after it (see below).

Success messages ("Added France.", "Undid France.") clear themselves after 5s via `setTimeout` (any previous pending clear is cancelled first, so a fast follow-up message isn't cut short); error messages are left up, since those may need reading/acting on. The undo button's disabled-during-request window covers only the `/undo_country` call itself, not `scheduleMapRefresh()` afterward -- re-enabling the button doesn't wait on the (slower, multi-MB) map redraw, so a second undo can fire immediately. `refreshCountriesMap()` itself is still funneled through one shared `mapRefreshChain` promise regardless of what triggers it (a submit or an undo, back to back or overlapping), so `Plotly.react()` calls stay strictly serialized -- calling it again before a previous call on the same mapbox subplot has finished is the same class of rendering-corruption risk the counties/states insets' `refitChain` (in the `mapbox_bounds_json` block above) exists to prevent, and submitting/undoing in quick succession hits it the same way overlapping resize events did there.

### "Flown through" countries
A country can now be marked "flown through" (flew over, didn't land) as a fact independent of "visited" -- `countries.flown_through`, a new boolean column alongside `visited`. `location_db.set_flown_through_country`/`set_visited_country` are two separate methods, each only ever setting its own column; neither clears the other, so a country can be both. Display-time code (see "Map treatment"/"Card list" below) is responsible for treating visited as taking priority when both are set, per an explicit design call: visited wins.

Written exactly to the standing schema-change rule at the top of "Database layer" above -- `flown_through` was added to the `Table()` def (so a brand new DB gets it for free via `create_all()`), plus an `ALTER TABLE ... default False` check in `locationDB.__init__` for every DB that pre-dates the column (which is every DB that exists right now, dev included -- confirmed live: before this change dev's `countries` table had 4 columns, after a restart it had 5, with all existing rows backfilled to `False` rather than `NULL`). The `.country-bar` form (see "Add Country autocomplete" above) got a second row: a "Flown through (not visited)" checkbox that changes which of the two `location_db` methods `/log_country` calls, rather than a new route.

**Map treatment**: the original plan was a hatched fill for flown-through-only countries, distinct from visited countries' solid color -- but `go.Choroplethmapbox`'s `marker` only exposes `opacity` and `line` (color/width), confirmed directly against plotly's own attribute schema; there's no `pattern`/`patternshape` the way SVG-based traces like `Bar` have, and no line-dash option either, so a literal hatch isn't available through this trace type's declarative API. Built a solid neutral tint instead (chosen over the alternatives by explicit user call): `serve_country_graph`'s stepped-colorscale scheme (see above, in this same section) now has 3 tiers instead of 2 -- category 0 = unvisited/never-flown (opacity 0, fully transparent), category 1 = flown-through-only (`#5B84B1`, a muted blue, at opacity 0.25), categories 2..N+1 = one per visited country (own `_country_color`, opacity 0.5, unchanged). "Visited supersedes flown-through" is enforced the same way in both places it matters: `color_category` only assigns a country to the flown-through bucket when `visited == False` (a visited-and-flown-through country lands in its own visited category instead), and `fill_opacity`'s `np.select` checks `visited` before `flown_through`. Hover also flags flown-through-only countries (`"Japan (flown through)"`) so it's not ambiguous why they're tinted differently from a plain unvisited country; visited/unvisited hover text is unchanged. Verified against real DB state (a country flagged both visited and flown-through resolves to the visited category/opacity/hover, not the flown-through one) before reverting the test data.

**Card list**: `_compute_country_cards` now builds up to two independent `<div class="state-grid">` blocks -- visited (unchanged), then, only when there's at least one, a flown-through-only one (same "visited supersedes" filter as the map) under a `<h2 class="country-section-header">Flown Through</h2>`. Two separate grid divs rather than one shared grid, specifically so the second section always starts on its own line regardless of how many columns the first grid happened to wrap into at a given screen width -- a block-level element boundary guarantees that in a way appending more cards to the same grid wouldn't. `_compute_country_card_grid` factors out the actual per-row card-building shared by both.

Confirmed working end to end on a real device: the map tint, hover text, and card-list section all render correctly, and visited still supersedes flown-through when a country is later marked both.

### County visit-years
`counties.year` only ever stored the *most recent* visit year (overwritten on each new visit) -- every intermediate year was computed by the ETL pipeline and silently discarded. This directly broke the `/counties` year slider: it's a cumulative "visited by year X" filter, which logically needs each county's *first* visit year, not its most recent one -- a county visited in both 2015 and 2022 only counted as visited once the slider reached 2022, not 2015. Deliberately no new UI for this (no per-county card list -- confirmed with the user: ~800 visited counties nationally isn't a useful flat list at any grouping short of a real per-state drill-down, which `/state_view` doesn't have and is its own separate task).

**Schema**: `county_visits(fips, year)`, composite PK, one row per distinct visit-year -- written exactly to the standing schema-change rule (new `Table()` def for a fresh DB, `insp.has_table()` check + `create_all()` for an existing one, same precedent as `counties`/`countries`'s own table-creation checks). `positions.county_visit_year_logged` is a second new column, independent of `county_processed` (self-migrating `ALTER TABLE`, same `flown_through` precedent) -- see "Backfill" below for why it has to be separate.

`location_db.set_visited_county` now unconditionally calls a new `record_county_visit_year(fips, year)` (select-then-insert-if-absent, matching the existing `get_user_id` idiom -- no `INSERT OR IGNORE` precedent in this codebase) before its existing max-year-cache logic runs. This is the *only* place that decision is made, so `counties.year`/`visited` keep meaning exactly what they meant before (a cache, still used for the base map color, `get_num_counties_visited`, `_compute_table`'s per-state counts, etc.) while `county_visits` becomes the real ledger underneath it -- additive, not a replacement. The current historical-GPX pipeline, `process_historical_points.py`, deliberately does *not* go through `set_visited_county` -- it calls `record_county_visit_year` directly, by design, so it can never touch `counties.visited`/`year`. `unset_county_by_fips` (a targeted correction, e.g. "this county was mis-detected") cascade-deletes matching `county_visits` rows too; `unset_all_points` (a blanket ongoing-pipeline reset) deliberately does not, so it can't destroy backfill-derived history as a side effect of resetting an unrelated cache -- an intentional asymmetry, not an oversight.

**Ongoing pipeline vs. backfill, one shared code path**: `CountyAdder(mode='ongoing'|'backfill')` sets `self.processed_column`/`self.visit_recorder`, threaded through `get_points_to_parse_dataframe`/`count_unprocessed_counties`/`set_point_county_processed`/`set_pointlist_county_processed` (each grew an optional `column` param, defaulting to `county_processed` -- zero change for any caller that doesn't pass one). `mode='ongoing'` (cron's default, unchanged behavior) tracks progress on `county_processed` and calls `set_visited_county`. `mode='backfill'` (`backfill_county_visit_years.py`, a new one-off script -- deliberately *not* a CLI flag on `add_county_visits.py`, whose bare `__main__` is what cron invokes directly, to make "accidentally run backfill mode on a schedule" structurally impossible) tracks progress on `county_visit_year_logged` instead and calls `record_county_visit_year` directly, bypassing the max-year cache entirely. Since `county_visit_year_logged` starts `False` on every row (including ones already `county_processed=True` from months/years of prior ongoing processing), a backfill run replays the *entire* history and, because `set_visited_county`'s dual-write is unconditional, recovers every intermediate year that ongoing processing computed-then-discarded along the way. It never touches `counties.visited`/`year` or `positions.county_processed` -- only `county_visits` and its own tracking column -- so it can't disturb what the live map currently shows, and is safe to run against a live site or in full against dev's DB as genuine validation, not just a smoke test. Resumable for free (kill it, re-run it, `iterate_until_done()` just picks up whatever's still unlogged).

`remove_frequent_counties`'s bbox shortcut needed a real fix here, not just mode-threading: it used to keep only the single globally-latest point per batch per frequent county and mark everything else in that box processed without ever recording a year -- meaning even post-backfill, a frequently-visited (e.g. home) county would still only ever get one year recorded per batch. Now groups by `(county, calendar year)` within the box and keeps the latest point per year instead of per batch -- still one polygon lookup per (frequent county × distinct year present in that batch), not per point, so the whole point of the shortcut is preserved. Applies to both modes automatically, since it's the same shared method.

**Cron/backfill overlap**: rather than manually pausing cron during a backfill run, `cronjob_daily.sh` and the backfill invocation share one `flock` lock (`/tmp/county_processing.lock`, confirmed present in the image -- `util-linux 2.38.1`). Cron's side is non-blocking (`flock -n`) -- if a backfill is already running, cron's invocation just exits immediately and silently, costing nothing until it fires again next hour. The backfill invocation is blocking (plain `flock`, no `-n`) -- it's a deliberate manual one-off, so if it happens to start while a routine (normally fast) cron cycle is mid-flight, it waits its turn rather than silently no-op'ing:
```
docker exec -d -w /project location_track_dev sh -c "flock /tmp/county_processing.lock -c 'python backfill_county_visit_years.py' > /tmp/backfill_log.txt 2>&1"
```
`record_county_visit_year`'s insert is also wrapped in `try/except IntegrityError` as cheap defense-in-depth against the narrow TOCTOU window in its select-then-insert idiom -- the lock should make this essentially unreachable in practice, but it's a harmless no-op either way if it ever triggers.

**Slider fix**: `serve_county_graph` now computes `firstVisitYear` (`{fips: min(county_visits.year) - 2000}`) and `countyHoverText` fresh on every request -- deliberately *not* folded into the cached `self.template` figure, because the existing cache-invalidation check (`num_visited`/`avg_county_year` changing) wouldn't reliably catch a backfill run adding an earlier year to an *already*-visited county; baking either into the cached figure would make them go stale indefinitely after a backfill, not just briefly. Threaded through the existing `mapbox_bounds_json` (already rebuilt fresh every request for the same reason the AK/HI zoom-correction bounds are). `templates/notdash.html`'s slider JS still colors from the original max-year `z` value, but the show/hide test now checks `firstVisitYear` instead -- a county visited in both 2015 and 2022 now correctly shows from 2015 onward. `year_min`/`year_max` (the slider's own range) similarly now come from the true global `MIN`/`MAX(county_visits.year)` rather than `counties.year`'s min-of-per-county-*maxes*, which could undercount how far back the slider's floor needs to reach.

**Bug found while testing the historical-points pipeline against the live UI**: `year_min`/`year_max` were computed correctly (the fix above), but still lived *inside* `__precompute_graph` -- the cached, gated computation -- not fresh per-request like `firstVisitYear` next to it. Since `record_county_visit_year` (every historical-points commit, and `mode='backfill'`) never touches `num_visited`/`avg_county_year`, adding an earlier year via either pipeline would never trip the cache-invalidation check, leaving the *running* server's `year_min` stuck at whatever it was computed as before -- exactly the same staleness trap `firstVisitYear`/`countyHoverText` were already built to dodge, just missed for this one value. Concretely: after committing a 2005 historical trip, the live server kept serving `yearRange: [2015, ...]` (its last-cached value) instead of `[2005, ...]`, meaning the slider couldn't physically reach 2005 at all, and (now that the color scale's `cmin` is also derived from this) the color range's floor was wrong too. Fixed by moving the whole computation out of `__precompute_graph` and into `serve_county_graph` itself, reusing the `years_by_fips` dict already fetched there -- structurally can't go stale now, matching `firstVisitYear`'s own reasoning exactly. `/states` never had this bug -- `serve_state_graph` computed its own `year_min`/`year_max` as plain per-request local variables from the start, never cached.

**Year-mode toggle ("Up to" / "Only")**: a second slider mode, added after real-browser testing surfaced that `/states` still had the exact same last-visited-year bug `/counties` had before the slider fix above -- it never got the same treatment, since `get_state_visits_dataframe` only ever aggregated the old `counties` cache (max year per county, then max of those per state), with no per-year history at all. New `location_db.get_state_visit_years_dict()` mirrors `get_county_visit_years_dict()` (join `county_visits` to `us_counties` on `fips`, group by state -- `.distinct()` matters here, unlike the county version, since multiple counties in one state visited the same year would otherwise duplicate). `serve_state_graph` now computes `firstVisitYear`/`visitedYears`/`countyHoverText` (reusing that same JSON key name from the counties page) exactly like `serve_county_graph` does, and `year_min`/`year_max` there now source from the true ledger min/max the same way `/counties` already did, falling back to the old computation only pre-backfill. Confirmed end-to-end against the real dev DB (not just mocked): OH shows all 12 years 2015-2026, `yearRange` is `[2015, 2026]` (previously wrong on `/states`, only ever fixed on `/counties`), hover reads "Ohio — 2015-2026" using `config.abbrev_to_us_state` (already existed, used elsewhere in this file -- no new lookup needed).

The toggle itself: `firstVisitYear` alone can't answer "was this visited in *exactly* year X", only "was it first visited on or before X" -- so counties/states now also ship `visitedYears` (`{fips_or_state: [full sorted year list]}`, same `-2000` offset convention), and the slider bar (`templates/notdash.html`) grew a segmented control (`#yearModeToggle`, two `.year-mode-btn` elements, `data-mode="cumulative"|"only"`) replacing the old plain "Through {year}" label. `applyYearFilter`'s cumulative branch is untouched (confirmed byte-identical via diff during verification); the new "only" branch checks `visitedYears[fips].indexOf(cutoffOffset)` and, on a match, assigns the flat z-value `cutoffOffset` itself (the slider's current year) to every match rather than each entity's own historical `v` -- deliberately flat/uniform coloring, since the existing gradient encodes "how long ago", which stops meaning anything once already filtered to one exact year; reuses the same shared `coloraxis` (via `Plotly.update`, see the color-scale rescale below), no new colorscale or trace. Hover text is unchanged in both modes (always the full history, not just the selected year). Landscape mode's fixed `.year-slider-bar` height grew from 220px to 260px to fit the extra control.

Verified via the Node mock-harness pattern established earlier this session, extended for the toggle: confirmed the copied IIFE is byte-identical (comments aside) to what's actually rendered, then exercised cumulative mode (regression -- exact match to pre-toggle output), "only" mode matching/non-matching entities at several cutoffs including the flat-color proof (two counties with different visit histories get the *same* z at a shared matching year), mode-switching both directions, and a no-op click on the already-active button. Also directly invoked `serve_county_graph`/`serve_state_graph` themselves (not just the DB layer or a JS mock) against the real dev DB end-to-end -- catches integration issues neither layer alone would (e.g. this is how a private-name-mangling gotcha calling `self.__mapbox_layout_base()` was caught during verification: works fine as an instance method, breaks if you ever call the unbound function with the bare class as `self` instead of a real instance).

**Color-scale rescale + displayed-count banner**: two follow-up requests once the toggle was confirmed working. (1) `coloraxis.cmax` now tracks the slider's own cutoff on every move (`Plotly.update`, not `Plotly.restyle`, since layout properties need `relayout`-style updates) instead of staying pinned to whatever the *global* most-recent year happened to be -- previously the gradient's top always meant "as recent as the latest visit anywhere," wasting most of the range on years past the current cutoff; now it means "as recent as what you're currently looking at," including in "only" mode, where every match then shares the single darkest/fullest color (since they all carry the same z as the cutoff) rather than landing at whatever position that year happens to occupy on a scale still ranging up to the global max. (2) `<h1>` grew a `#displayedCount` span, updated every `applyYearFilter` call: `(N visited up to {year})` or `(N visited only in {year})` depending on mode. Counted from trace 0 (the main map) only, not summed across all traces -- the AK/HI inset traces redraw a *subset* of the same counties/states already in the main trace, so summing would double-count them.

**Two real bugs found testing this against real historical data (post-full-run), both now fixed**: the user reported historical counties "never show in Only mode, and only show in Up-to mode during their exact year" -- traced end-to-end using a concrete case, Windsor County, VT (`counties.visited=True`/`year=2005`, but *zero* `county_visits` rows -- a leftover from the old pre-ledger `add_historical_counties.py` seeding, part of the already-documented "216 counties" gap).

**Historical GPX points: `historical_points` table, not `positions`.** Two prior approaches, both now superseded. `add_historical_counties.py` (computes county from a GPX file, calls `set_visited_county` directly -- raw points never stored) was superseded earlier this session by `add_historical_gpx_points.py` (inserts each point as a genuine `positions` row with a synthesized timestamp, so the standard `add_county_visits.py`/backfill pipeline picks it up automatically). That approach was then itself reconsidered: mixing synthetic points into the same table as real device-logged GPS blurred what `positions` represents, and the whole synthesized-timestamp exercise (distance/speed math, trip-spacing, a per-trip span assertion, all to survive `add_county_visits.py`'s flyover-speed filter) is unnecessary for a dedicated table with its own dedicated processor. Both `add_historical_counties.py` and `add_historical_gpx_points.py` have since been deleted -- nothing in prod ever depended on either; only synthetic test points were ever inserted through the latter, already cleaned up before removal.

Current design: a new `historical_points` table (`id`, `source_file`, `year`, `latitude`, `longitude`, `county_computed`, `fips` -- self-migrating per the standing rule, `location_db.py`'s existing-DB branch) stores raw points with *only* their known calendar year, nothing synthesized -- no timestamp, no speed, no trip-spacing. Two scripts:
- **`load_historical_points.py`** -- owns its own `(filename, year)` manifest (same values as `add_historical_gpx_points.py`'s, now vestigial there), parses GPX (`load_points`, flattens all tracks/segments), and batch-inserts a file's points via the new `location_db.insert_historical_points_batch` -- one `executemany`-style insert + commit per file, not a commit per point like `insert_location` (fine for that method's single-point real-time use case, far too slow for tens of thousands of points at once). Skips any manifest entry whose `source_file` is already loaded (`get_loaded_historical_source_files`), so re-running after adding new files to the manifest only loads what's new.
- **`process_historical_points.py`** -- point-in-polygon lookup (same `geoData[...].contains(Point(...))` idiom `CountyAdder._look_up_county` uses, done inline rather than instantiating `CountyAdder`, since none of its `positions`-oriented setup or speed-filtering is relevant here) for any `county_computed=False` row, with a cheap same-county-as-the-previous-point short-circuit. The resolved `fips` is normalized to the 5-char form (`counties.fips`'s own format) at this point, not deferred -- it gets persisted, unlike the rest of the pipeline where raw `GEO_ID` flows through until the final write. Regardless of whether that step found new work, the script *always* regroups every row by `source_file` afterward to re-derive each file's distinct county set and re-run the cross-validation check below, making the whole script safe to re-run any time (idempotent, and even flag resolution re-evaluates against live DB state for free -- no separate approved-list bookkeeping).

**Cross-validation before writing to `county_visits`**: some of these GPX files were *recreated* by the user rather than recovered originals (e.g. the consolidated `raleigh_1.gpx`/`raleigh_2.gpx`, replacing 4 original files), so a genuinely new/uncorroborated county from one of them is a plausible sign of a route error -- the same principle the "future idea" note below already lays out for the (still unpursued) Google-routing idea, applied here to recreated files instead. Before committing, each (file, county) pair is checked via the new `location_db.has_any_county_evidence(fips)`: true if either `counties.visited` (the cache -- catches real ongoing-pipeline visits and the old pre-`county_visits` `add_historical_counties.py` seeding) *or* `county_visits` has any row for that fips (catches recent GPS-derived backfill visits, and this pipeline's own prior commits) is true -- checking `counties.visited` alone isn't enough, since `record_county_visit_year` (used for every commit here, deliberately, so this pipeline can never disturb `counties.visited`/`year` -- the live map's base color -- same "backfill can't touch the cache" principle `mode='backfill'` follows in `add_county_visits.py`) never updates it. A hit gets written immediately; a miss is held back and printed in a "flagged" summary instead. Approving a flagged county is a one-off `database.record_county_visit_year(fips, year)` call (same pattern used for the Kane/Blackford/Glacier/Atlantic County check earlier this session) -- picked up automatically on the next run.

  - **Not scoped or fixed this session.** Predates all of this session's work.
