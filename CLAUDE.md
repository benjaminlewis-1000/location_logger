# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal location-tracking web app ("OwnTracks"-style). Phone GPS loggers (OwnTracks, ulogger, GPS Logger) POST position pings to a Flask server, which stores them in SQLite and renders Google Maps views of tracks, plus choropleth maps (via Plotly) of US counties/states/countries visited. Runs as a single Docker container behind a Cloudflare tunnel + Traefik, with Authelia handling auth on most routes.

## Running it

There is no local dev workflow beyond running the Flask app directly — this project is normally deployed via Docker Compose on the host machine, not run/tested by a coding agent.

- `docker-compose up --build` — builds from `config_files/Dockerfile` and starts the `location_track` service (container command: `sh /project/config_files/startup.sh`).
- `config_files/startup.sh` starts `cron` and launches gunicorn on `serve_flask_interface:app` (port 5000).
- Local/manual run (outside Docker): `python serve_flask_interface.py` runs Flask's dev server on port 8090.
- Requires a `.env` file (see `.env_template`) with `WEBAPP_DOMAIN`, `PASSWORD`, `GMAP_API_KEY`.
- No test suite or linter is configured. `test_flask.py` is a legacy/experimental copy of the Flask app, not a pytest suite.

### Data locations
- SQLite DB path is set in `config.py` (`database_location`, currently `/data/location.sqlite`). In the container, `/data` is bind-mounted from `/mnt/fast_storage/appdata/location_tracks`.
- The whole repo is bind-mounted into the container at `/project` (see `docker-compose.yml`), so code changes take effect without rebuilding the image — only a container restart is needed unless dependencies change.

## Architecture

### Database layer — `location_db.py`
`locationDB` wraps a SQLAlchemy Core (not ORM) SQLite database with four tables: `positions` (raw GPS points), `users` (maps a device/user string to an id), `counties` (all US counties, FIPS-keyed, with `visited`/`year`), `countries` (world countries, with `visited`). It self-migrates on construction (adds missing columns/tables via `ALTER TABLE`/`create_all`, checked on every startup) and seeds `counties`/`countries` from `config_files/state_and_county_fips_master.csv` and `config_files/countries.csv` if empty. Almost all cross-file interaction with data goes through this class — there is no ORM model layer elsewhere.

**Rule (not a todo, a standing constraint): every schema change must self-migrate on startup, unconditionally.** Dev's database was cloned from prod once (see "Dev environment" below) and has been fully independent ever since — nothing done to it here ever reaches prod's database, including by merging code. So when this branch eventually merges and prod runs the new code, prod's database will still be on the *old* schema at that moment; there is no shared migration step that runs once at deploy time. A new column/table can never be assumed to exist just because it does in dev, or because a fresh DB would have it — the code itself has to detect the absence and add/backfill it, every time, the same way `__init__` already does for the `year`/`county_processed` columns, `populate_countries`/`populate_county_table` seeding empty tables, and the Namibia `code_2`/`code_3` NULL repair. Any future schema addition (e.g. a "flown through" country/table) needs the same treatment, not a one-off migration script.

### Web layer — `serve_flask_interface.py`
The live entrypoint (`serve_flask_interface:app`, per `startup.sh`). Uses `flask_classful`'s `FlaskView` (class `FlaskApp`) to define routes as methods; `FlaskApp._initilization()` is called once at import time (a documented hack, see comment at bottom of file, to work around `flask_classful` re-running `__init__` per request). Key routes:
- `/` — main Google Map view of tracked points/polylines over a date range (`start`/`end` query params); `?points=1` switches from a polyline to individual deletable markers.
- `/log`, `/client/index.php` — ingestion endpoints for OwnTracks (`/log`) and ulogger (`/client/index.php`) apps.
- `/counties`, `/states`, `/countries`, `/state_view` — Plotly choropleth dashboards of visited areas, rendered into `templates/notdash.html`.
- `/log_flight` — scrapes a FlightAware KML URL and inserts it as a track (see also `addpoints_flightaware_kml.py`).
- `/execute_delete` — deletes a point by id (used by the marker delete-button popups on `/?points=1`).
- Most routes are gated by `@authelia_required`, which checks/verifies an `authelia_session` cookie against an external Authelia instance (`AUTHELIA_URL`); ingestion routes (`/log`, `/client/index.php`) are intentionally left open so logger apps can POST without a browser session.
- `plotly_flask.py` is an older/alternate version of this same app — not the one actually served; check `startup.sh`/`docker-compose.yml` before assuming which file is live.

### County/state "visited" computation — `add_county_visits.py`
Run periodically via cron (`config_files/cronjob_daily.sh` → `add_county_visits.py`), not on the request path. `CountyAdder` walks unprocessed `positions` rows in time order and does point-in-polygon lookups against the county GeoJSON (`config_files/gz_counties_*.json`, loaded via geopandas) to mark counties visited. Two optimizations that matter when touching this file:
1. `config.frequent_counties`/`frequent_areas` are bounding boxes for places visited often; points inside them are handled by cheap bbox checks (only the latest point per pass is polygon-tested) instead of a full GeoJSON lookup for every point.
2. `calculate_speeds` estimates speed from neighboring points and filters out points faster than `speed_thresh` (45 m/s) so that airplane flights don't falsely mark every county overflown as "visited."
Points are marked `county_processed` once handled so re-runs are incremental.

### Data ingestion scripts (one-off / cron, not imported by the web app)
Each of these populates `positions` via `location_db.insert_location`, from a different data source: `addpoints_google_takeout.py` (Google Takeout location history), `addpoints_gpx_google.py`/`add_gpx_route_certain_time.py` (GPX files), `addpoints_csv_flightradar.py`/`addpoints_flightaware_kml.py` (flight tracking exports), `add_historical_counties.py` (backfilling county visits for historical/manual data). `cleanup_remove_spurious_areas.py` and `tmp_show_one_state.py` are maintenance/debug utilities. `config_files/cronjob_15_min.sh` runs `addpoints_gpx_google.py` every 15 minutes.

### Travelling salesman experiments
`travelling_salesman.py` and `google_travelling_salesman.py` are standalone route-optimization experiments (using `python_tsp`, `fast_tsp`, `ortools`) against `config_files/usa3100_mixed.tsp` — unrelated to the location-logging/visited-counties functionality and not wired into the Flask app.

### Config — `config.py`
Central place for file paths (all under `config_files/`), the `frequent_counties`/`frequent_areas` bounding boxes used by `add_county_visits.py`, and the US state name ↔ abbreviation maps used throughout the templates and Flask routes. Import `config` rather than hardcoding these paths/maps elsewhere.

## Dev environment (this worktree)

This directory is a `git worktree` of `location_track` (prod), checked out on a separate branch, sharing the same `.git` history — commits made here are immediately visible from the prod checkout via `git log`, no push/pull needed. It runs as its own Docker container (`location_track_dev`, image `location_dev_img`) alongside prod, on its own DB copy (`/mnt/fast_storage/appdata/location_tracks_dev/location.sqlite`, cloned once from prod and now independent) and its own tunnel hostname (`dev_owntracks.exploretheworld.tech`). `config_files/startup.sh` here runs gunicorn with `--reload` and `serve_flask_interface.py` sets `TEMPLATES_AUTO_RELOAD = True` — both dev-only conveniences (not present in prod) so `.py` and template edits show up on refresh without a manual container restart. Prod (`location_track`, `main` branch, container `location_track`) intentionally lacks these.

**`--reload` gotcha: it only recovers from per-request errors, not import-time ones.** If an edit introduces an error that happens at *module import* (e.g. `_initilization()` throwing, or a bad top-level import) rather than inside a request handler, the gunicorn worker fails to boot at all, and after enough failed boot attempts gunicorn's **master** process gives up and exits too — taking `--reload`'s file-watcher down with it. The container itself stays "Up" (`config_files/startup.sh`'s own `while true; do sleep 10; done` is what Docker is actually watching, and `cron` is a separate process), but the site is fully down and no further file save will trigger a reload, since the thing that watches files is gone. Recovery: fix the bug, then manually relaunch gunicorn inside the container rather than just waiting for auto-reload:

```
docker exec -d -w /project location_track_dev sh -c "/usr/local/bin/python /usr/local/bin/gunicorn --reload -b 0.0.0.0:5000 serve_flask_interface:app > /tmp/manual_gunicorn.log 2>&1"
```

Redirect to a file (as above) rather than a bare `docker exec -d ... gunicorn ...` -- `docker exec -d` output doesn't appear in `docker logs` at all, so an unredirected manual launch that crashes again later leaves *nothing* to diagnose it from (this bit once already: a second, still-unexplained crash left only the first crash's now-stale trace visible in `docker logs`). Confirm the relaunch actually came up with a real request (`docker exec location_track_dev python3 -c "import requests; print(requests.get('http://localhost:5000/<route>', allow_redirects=False).status_code)"`) rather than trusting the log tail either way.

## Working conventions

**Explain the plan before implementing it, for anything with real design surface.** New features, schema/DB changes, anything touching multiple files or with more than one reasonable way to build it — say what's about to be built and how (the approach, the pieces/files involved, any real tradeoffs) *before* writing the code, not only after in a summary. Small, obvious, single-file tweaks (a color, a size, a threshold number, a one-line fix) don't need this ceremony — use judgment on which category a change falls into.

**Verify Plotly/mapbox-gl trace capabilities empirically before building on them — don't assume by analogy.** This app leans on several non-obvious trace tricks that do work (a stepped colorscale for discrete per-location colors, a transparent-fill overlay trace for a borders-only layer, per-location `marker.opacity` arrays) but aren't obviously documented as supported. Two things were assumed available and weren't, both on `/countries`' micro-country markers: `marker(symbol='star')` (needs a Mapbox access token this app deliberately doesn't have) and `mode='text'` markers reliably rendering (a mapbox-gl *symbol* layer has collision detection on by default, which can silently drop the marker, and Plotly's declarative API doesn't expose the style-spec property to turn that off — see "Countries map" below for the full story). When a trace attribute's behavior matters, check it directly (e.g. `dir(go.Choroplethmapbox().marker)`, or plotly's own schema/docs) rather than assuming it exists because a similar-looking trace type has it.

**No real browser is available for verifying JS changes here — this environment has neither one nor `jsdom`.** The pattern used throughout this branch: render the real template server-side (Flask's `render_template`/test client) to get genuine output, extract the relevant `<script>` block, `node --check` it for syntax, and for anything with real control flow (the Add Country form, undo stack, zoom-scaling), copy the function bodies verbatim into a small Node script that mocks just enough of `document`/`fetch`/`localStorage`/`Plotly` to exercise the actual logic and assert on outcomes. This has repeatedly caught real bugs (a stray `#`-vs-`//` comment typo, twice; wrong assumptions in a hand-written test's own expected values) before they reached the user, but it's still not a substitute for the genuinely-only-real-browser-catches-it class of bug (the two mapbox-gl rendering misses above were both invisible to this whole toolchain and only found by the user on an actual device) — UI changes should still be reported as unconfirmed until the user actually looks at them.

### Counties map (`/counties`)
Rebuilt around three `go.Choroplethmapbox` subplots (continental US, plus small Alaska/Hawaii insets — mapbox has no native inset projection the way the old `scope="usa"` geo trace did) instead of a single static geo/choropleth trace, because the old geo trace was a fixed-aspect SVG projection that always letterboxed inside a mismatched container and couldn't be fixed with CSS alone. Alaska/Hawaii bounds/center/zoom are computed at startup in `FlaskApp._initilization()` via geopandas (see `_mercator_y`/`_mercator_center_lat`/`_fit_zoom`/`_pad_bounds` module-level helpers) and corrected again client-side in `notdash.html`'s JS after the page loads, since the server can't know the visitor's actual screen size. A horizontal/vertical (by orientation) slider replaced the static "Year" colorbar; see the schema-change note above for its current data limitation.

Alaska/Hawaii's counties are colored on the main subplot's trace *in addition to* their dedicated insets, not instead of them -- the insets stay for an always-visible view, but since the main map is a real pannable/zoomable tile map now (not a fixed projection), panning/zooming out far enough to actually reach Alaska or Hawaii's true location should show them colored rather than a blank basemap. Same treatment on `/states`' main trace.

A 4th trace overlays state boundaries on the main subplot (`/counties` only -- on `/states` the choropleth polygons already *are* state boundaries, so it'd be redundant there): `self.states_geojson` again, transparent fill (`colorscale=[[0,'rgba(0,0,0,0)'],[1,'rgba(0,0,0,0)']]`, its own standalone colorscale rather than the shared `coloraxis`, so it can't ever pick up a real fill color) and a thicker/darker line (`1.5`/`#333`) than the county borders beneath it (`0.4`/`#888`), so state lines stay readable at a glance even zoomed into county-level detail. `hoverinfo='skip'` keeps it from swallowing hover tooltips meant for the county layer. It does still carry a (constant, all-zero) `z` array, so the year-slider JS includes it in every `Plotly.restyle` call along with the real traces -- harmless (0 never exceeds any realistic cutoff, confirmed against the actual rendered data), just a few unnecessary bytes per slider move, not worth the complexity of excluding it.

### Countries map (`/countries`)
Same `go.Choroplethmapbox` approach as counties, but one full-domain subplot (a world view has no AK/HI-style inset problem). Fill opacity is per-country (`marker.opacity` takes an array, same as `z`): 0 for unvisited so the basemap shows through untinted, 0.5 for visited so it's still partly visible under the color. Borders stay fully opaque regardless -- `marker.line` (the border) is a separate style layer from the fill in mapbox-gl, with its own independent opacity, so country outlines remain visible everywhere. Country boundaries come from `config_files/world-countries.geojson` (238 features, `id`'d by ISO alpha-3 to match `location_db`'s `countries.code_3`/`countries.csv`'s `alpha-3`), generated once from https://github.com/datasets/geo-countries (itself Natural Earth-derived) with two fixups applied before vendoring it in: large countries' coastlines simplified (`shapely.simplify`, ~2km tolerance, only for countries whose bbox exceeds 3°) to cut the file from 14.6MB to 2.9MB, and France/Norway's ISO codes — which that source leaves as the placeholder `"-99"`, a known issue in Natural Earth-derived country datasets — corrected by name lookup against `countries.csv`. 20 non-ISO/disputed territories (Kosovo, sovereign base areas, uninhabited islands, etc.) were dropped entirely since nothing in this app can ever mark them "visited" anyway; 11 more (French/Dutch overseas departments, a few uninhabited islands) aren't broken out as separate shapes in the source data and so can't be shown individually if ever marked visited — both are cosmetic edge cases, not routes to a broken page.

Each visited country gets its own color (`_country_color`) rather than one shared "visited" color, so adjacent visited countries don't blend into a single blob -- explicitly *not* real four-color-theorem map coloring (no adjacency data, no constraint solving), just a hash-seeded HSL hue per ISO code with fixed saturation/lightness (so every color comes out equally vivid regardless of hue) -- two neighboring countries can in principle still land on similar colors, an accepted tradeoff for staying simple. Hashed rather than using `random` so a given country's color is stable across reloads instead of reshuffling every page load. Technique: since a single `z`/`colorscale` normally produces one continuous gradient, each country is given its own "category" (0 = unvisited, sharing a single neutral color; 1..N = one per visited country) and the colorscale is built with two stops at the start/end of each category's slice (same color at both), which makes plotly render a hard-edged flat block per category instead of interpolating between them. Hover is overridden (`hovertemplate` + `customdata`) to show just the country name -- by default it'd show the `locations` value (the iso_3 code) and this internal category `z`, neither meaningful to a viewer.

Visited micro-countries (Vatican, and any similarly tiny country visited in the future -- Monaco, San Marino, etc.) are a sub-pixel dot on a world map even though they're technically colored; flagged by bounding-box diagonal (<0.5°, picked from eyeballing the real size distribution -- catches true microstates without also flagging small-but-still-visible countries like Luxembourg or Qatar) and given a marker at their centroid instead, on a second `go.Scattermapbox` trace. Two approaches were tried and discarded before landing on a plain circle (`mode='markers'`):
- `marker(symbol='star')` -- Scattermapbox's icon-based marker symbols come from Mapbox's own hosted sprite set, which needs a Mapbox access token this app deliberately doesn't have (it uses the free, tokenless `carto-positron` style specifically to avoid that).
- `mode='text'` with a unicode star glyph -- avoids the token problem, but confirmed invisible on a real device (Vatican, zoomed into Rome). Best explanation: this compiles to a mapbox-gl *symbol* layer, and symbol layers have collision detection on by default -- if mapbox-gl decides the glyph would overlap a basemap label (a city/sea name, etc.) at that zoom, it silently drops it, and Plotly's declarative Scattermapbox API doesn't expose the underlying style-spec property (`text-allow-overlap`) to disable that.

`mode='markers'` (a plain circle) compiles to a mapbox-gl *circle* layer instead, which isn't part of that collision system -- it always draws regardless of nearby labels. This is a reasoned fix for a bug that could only be confirmed on a real device, not reproduced locally -- worth re-checking if micro-country markers ever go invisible again.

The page also carries the same card-grid list styling `_compute_table` uses for `/states` (via a new `_compute_country_cards` — cards have no href, since there's no per-country drill-down page the way `state_view` drills down from a state). This is the first page to combine a full-bleed map with a table: those were previously mutually exclusive, selected implicitly by whether `more_html` was passed (table ⇒ contained 55vh map, no table ⇒ full-bleed). Now there's an explicit `full_bleed_map` flag passed to `render_template` (`/counties`, `/countries`, and now `/states` set it; `state_view` alone doesn't), and `notdash.html`'s CSS lets a `.table-container` coexist with the fixed-position full-bleed `#chart`.

The first version pushed the table down with `margin-top: 100svh` so the map was fully visible on load, with the card list meant to scroll up over it like a bottom sheet -- but on mobile this trapped scrolling entirely. `#chart` is `position: fixed`, so at 100svh tall it covers the *whole* viewport at *every* scroll position, not just at the top; combined with `touch-action: none` (needed so a drag pans the map instead of the page), that left no spot on screen a touch could land on to start a native scroll once the header bars scrolled out of view -- stuck with neither the buttons nor the table reachable, un-recoverable short of reloading. Fixed by adding a `with-table` body class (set when a page is both `full_bleed_map` and has `more_html`) that caps `#chart` to 90vh/90svh instead of 100 on those pages only -- `/counties` alone is untouched and stays full 100svh, since it has nothing to scroll to in the first place. The remaining 10% is never covered by the fixed map regardless of scroll position, so there's always a strip native touch-scroll can grab. This fix has not yet been re-confirmed on a real device.

Also found (fixed in the same pass): the autocomplete dropdown from `.country-bar` (below) was rendering *behind* `.title-bar`'s text. Not a plain z-index magnitude problem -- `.country-bar` had `position: relative` promoting it to its own stacking context (needed for the "paint above the fixed map" treatment all the header bars get), so the dropdown's z-index only ranked it against siblings *inside* `.country-bar`; the bar itself was tied at z-index:1 with `.title-bar` and lost that tie by coming first in the DOM. Fixed by giving `.country-bar` its own higher z-index (3) rather than sharing the combined `.top-bar, .country-bar, .title-bar` rule.

### States map (`/states`)
Same rebuild as counties/countries: `go.Choroplethmapbox` (continental + AK/HI insets, states has the same "Alaska is far away" problem) replacing the old `px.choropleth(scope='usa')`, full-bleed layout (`full_bleed_map=True`) with the existing `_compute_table` card grid below it (unchanged -- same cards `/states` always had, just now sitting under a real map instead of a letterboxed one). Colored by visit year, like counties -- unlike `/countries`, states does track a year (`location_db.get_state_visits_dataframe`), so this got the year gradient + slider instead of countries' binary visited/unvisited color; `get_state_visits_dataframe` now applies the same -2000 offset `get_county_visits_dataframe` does, since both feed the same slider JS (which hardcodes `YEAR_BASE = 2000`) -- it didn't before, since nothing consumed it that way yet.

State outlines needed a states-level GeoJSON, which didn't exist -- rather than sourcing another external file (as `/countries` needed to), `_initilization()` now dissolves the county polygons already loaded for `/counties` up to state boundaries via `geopandas.dissolve()`, keyed by the FIPS→state mapping `get_county_visits_dataframe()` already provides. Adds a few seconds to every startup (dissolving ~3200 county polygons into 51 states); state outlines aren't simplified the way `world-countries.geojson`'s large countries are, so the resulting file is comparably sized to the county one despite having far fewer features -- untouched so far since nothing's indicated it needs to be, not because it was checked and found fine.

The Alaska/Hawaii inset math (domain/zoom/center/pan-bounds) was previously computed inline inside the counties precompute method; pulled out into a shared `__mapbox_layout_base()` helper so `/states` doesn't duplicate it -- purely geometric, independent of whether counties' or states' data ends up colored on top. Confirmed byte-identical inset output for both pages post-extraction.

### Add Country form
The `.country-bar` form (shared top nav, present on every page) filters the full country list client-side as you type, matching name or either ISO code, ranked so "starts with" matches (including exact code matches) come before "contains" matches, capped to 8 shown. Picking a suggestion just fills the input -- submission is still the existing explicit Submit button/Enter, no auto-submit-on-pick. The full name/code list is precomputed once as `FlaskApp.country_list_json` in `_initilization()` (static once seeded, no need to requery per request) and injected into every template via `@app.context_processor` (`inject_country_list`), since the form isn't tied to any one route.

Building this surfaced a real pre-existing data bug: pandas' default NA-sentinel list includes the literal string `"NA"`, which is Namibia's actual ISO alpha-2 code, so it silently read as a missing value while seeding the DB from `countries.csv` -- Namibia's `code_2` was `NULL` in the database (confirmed to be the only country affected; checked the whole CSV against pandas' full sentinel list). Fixed both ends: `keep_default_na=False` on the CSV read prevents it on any future fresh seed, and `locationDB.__init__` now self-heals any existing NULL `code_2`/`code_3` row by looking it up from the CSV by name on every startup (a no-op once fixed, same "repair on startup if needed" pattern the schema-migration checks above it already use).

**Submission** is a `fetch()` POST (`event.preventDefault()` on the form's `submit`), not a normal browser navigation -- it used to land on `/log_country`'s raw JSON response as its own page. Success/failure now shows as a small inline message next to the form instead (`#country-form-message`); `/log_country`'s "identifier not found" path was changed from rendering `404.html` to returning JSON with the rest, since the client needs one consistent response shape to parse regardless of outcome. On success, only on `/countries` (the only page an added country could visibly affect), the map and card list refresh in place: rather than reimplementing the color/opacity/category logic in JS (which would need to exactly match `_country_color`'s Python-side hashing to avoid a country's color drifting between this live update and the next real reload), it re-fetches the current page's own HTML in the background, pulls the freshly-rendered `graphJSON` and `.table-container` back out of it, and applies them via `Plotly.react()` -- reusing the real server-side rendering rather than duplicating it. Known small gap: if this live refresh causes a micro-country star marker to appear for the first time (e.g. just marked Vatican visited while already on the page), it won't have the zoom-scaling behavior (see "Countries map" above) until an actual reload, since that listener is only ever attached once at initial page load.

**Undo** is a single button (`#undo-country-btn`, hidden when there's nothing to undo) backed by a LIFO stack in `localStorage` (`countryUndoStack` -- `localStorage`, not `sessionStorage`, specifically so it's shared across tabs of the same browser, not just page reloads within one). Each click pops the most recent `{iso_3, name, field}` entry and POSTs it to a new `/undo_country` route, which just forces that one column back to `False` via new `unset_visited_country`/`unset_flown_through_country` methods (mirrors of the existing setters). Clicking repeatedly walks back through the whole session's history, most-recent-first -- there's no separate "undo everything" action, since that's the same thing as clicking this one enough times.

The one real subtlety: not every successful submission is safe to undo. `/log_country` now looks up a country's status *before* mutating it (`get_country_status`, using a `_find_country_row` helper factored out of the three now-similar lookups in `location_db.py`) and includes `was_already_set` in its response; the client only pushes an undo entry when that's `False`. Otherwise, resubmitting a country that's already set (an accidental double-click, or just forgetting it was already added) would push an entry whose "undo" -- forcing the field back to `False` -- could silently erase a fact that's actually true from a completely different, untracked action. A failed undo request puts the popped entry back on the stack rather than losing it, and the button disables itself for the duration of a request to avoid a double-click racing two pops of the same top-of-stack entry -- but only for the actual `/undo_country` round-trip, not the map redraw after it (see below).

Success messages ("Added France.", "Undid France.") clear themselves after 5s via `setTimeout` (any previous pending clear is cancelled first, so a fast follow-up message isn't cut short); error messages are left up, since those may need reading/acting on. The undo button's disabled-during-request window covers only the `/undo_country` call itself, not `scheduleMapRefresh()` afterward -- re-enabling the button doesn't wait on the (slower, multi-MB) map redraw, so a second undo can fire immediately. `refreshCountriesMap()` itself is still funneled through one shared `mapRefreshChain` promise regardless of what triggers it (a submit or an undo, back to back or overlapping), so `Plotly.react()` calls stay strictly serialized -- calling it again before a previous call on the same mapbox subplot has finished is the same class of rendering-corruption risk the counties/states insets' `refitChain` (in the `mapbox_bounds_json` block above) exists to prevent, and submitting/undoing in quick succession hits it the same way overlapping resize events did there.

### "Flown through" countries
A country can now be marked "flown through" (flew over, didn't land) as a fact independent of "visited" -- `countries.flown_through`, a new boolean column alongside `visited`. `location_db.set_flown_through_country`/`set_visited_country` are two separate methods, each only ever setting its own column; neither clears the other, so a country can be both. Display-time code (not yet built, see below) is responsible for treating visited as taking priority when both are set, per an explicit design call: visited wins.

Written exactly to the standing schema-change rule at the top of "Database layer" above -- `flown_through` was added to the `Table()` def (so a brand new DB gets it for free via `create_all()`), plus an `ALTER TABLE ... default False` check in `locationDB.__init__` for every DB that pre-dates the column (which is every DB that exists right now, dev included -- confirmed live: before this change dev's `countries` table had 4 columns, after a restart it had 5, with all existing rows backfilled to `False` rather than `NULL`). The `.country-bar` form (see "Add Country autocomplete" above) got a second row: a "Flown through (not visited)" checkbox that changes which of the two `location_db` methods `/log_country` calls, rather than a new route.

**Map treatment**: the original plan was a hatched fill for flown-through-only countries, distinct from visited countries' solid color -- but `go.Choroplethmapbox`'s `marker` only exposes `opacity` and `line` (color/width), confirmed directly against plotly's own attribute schema; there's no `pattern`/`patternshape` the way SVG-based traces like `Bar` have, and no line-dash option either, so a literal hatch isn't available through this trace type's declarative API. Built a solid neutral tint instead (chosen over the alternatives by explicit user call): `serve_country_graph`'s stepped-colorscale scheme (see above, in this same section) now has 3 tiers instead of 2 -- category 0 = unvisited/never-flown (opacity 0, fully transparent), category 1 = flown-through-only (`#5B84B1`, a muted blue, at opacity 0.25), categories 2..N+1 = one per visited country (own `_country_color`, opacity 0.5, unchanged). "Visited supersedes flown-through" is enforced the same way in both places it matters: `color_category` only assigns a country to the flown-through bucket when `visited == False` (a visited-and-flown-through country lands in its own visited category instead), and `fill_opacity`'s `np.select` checks `visited` before `flown_through`. Hover also flags flown-through-only countries (`"Japan (flown through)"`) so it's not ambiguous why they're tinted differently from a plain unvisited country; visited/unvisited hover text is unchanged. Verified against real DB state (a country flagged both visited and flown-through resolves to the visited category/opacity/hover, not the flown-through one) before reverting the test data.

**Card list**: `_compute_country_cards` now builds up to two independent `<div class="state-grid">` blocks -- visited (unchanged), then, only when there's at least one, a flown-through-only one (same "visited supersedes" filter as the map) under a `<h2 class="country-section-header">Flown Through</h2>`. Two separate grid divs rather than one shared grid, specifically so the second section always starts on its own line regardless of how many columns the first grid happened to wrap into at a given screen width -- a block-level element boundary guarantees that in a way appending more cards to the same grid wouldn't. `_compute_country_card_grid` factors out the actual per-row card-building shared by both.
